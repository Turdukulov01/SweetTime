# Постоянные заказы V2

Статус: реализовано локально, production rollout и физическая приёмка ожидаются.  
Дата решения: 2026-07-27.  
V2 расширяет, но не отменяет планировщик из
[`RECURRING_ORDERS_V1.md`](RECURRING_ORDERS_V1.md).

## Пользовательская модель

- У клиента может быть до 20 независимых активных постоянных заказов.
- В каждом заказе можно выбрать до 20 товаров, свой филиал, время, комментарий
  и период: 1, 7 или 30 ежедневных выдач.
- Каждый постоянный заказ имеет стабильный ID и редактируется отдельно.
- Можно добавить или убрать товары, поменять филиал, время, комментарий и
  оплаченный период.
- Сервер фиксирует состав, локализованные названия, фото, размер и цену каждой
  позиции. Позднее изменение или деактивация товара в каталоге не меняет уже
  оплаченные выдачи.
- После изменения сервер пересчитывает только будущие выдачи, для которых
  ежедневный заказ ещё не сформирован. Уже созданный заказ на сегодня остаётся
  неизменным.
- При отмене уже созданный заказ на сегодня остаётся, а за оставшиеся ещё не
  сформированные выдачи записывается расчётный кредит.
- Просроченные и отменённые постоянные заказы не выдаются как активные в
  мобильное приложение.

## Важное ограничение оплаты

Сейчас используется `settlementMode=mock`. Доплата и кредит рассчитываются,
версионируются и записываются в журнал, но реальные деньги не списываются и не
возвращаются. До подключения банка/PSP интерфейс обязан везде показывать
пометку «демо».

Для реальной оплаты потребуются:

1. платёжный intent для создания и положительной корректировки;
2. refund либо баланс клиента для отрицательной корректировки;
3. webhook с идемпотентной фиксацией результата;
4. состояние `pending/paid/failed/refunded`, а не только `mock`;
5. постоянный outbox/idempotency key на устройстве для восстановления после
   потери ответа.

## API

Клиент:

- `GET /api/companies/{companyId}/auth/customer/me/recurring-orders`
- `POST /api/companies/{companyId}/auth/customer/me/recurring-orders`
- `PATCH /api/companies/{companyId}/auth/customer/me/recurring-orders/{id}`
- `DELETE /api/companies/{companyId}/auth/customer/me/recurring-orders/{id}`

`POST` и `PATCH` принимают `Idempotency-Key`. `PATCH` принимает `baseVersion`;
конфликт параллельного редактирования возвращает HTTP 409.

Старый singleton API оставлен только для совместимости старых APK. Его PATCH
делегирует финансовый пересчёт V2, чтобы старое приложение не могло бесплатно
увеличить оплаченный состав.

Админка:

- `GET /api/companies/{companyId}/analytics/recurring-orders`
- доступ только владельцу и менеджеру;
- возвращает количество активных подписок, созданные и завершённые сегодня
  постоянные заказы, сегодняшние положительные корректировки, дневную
  обязательную сумму и строки по клиентам.

В строке видны клиент, телефон, зафиксированные товары и фото, филиал, время,
план, дата оплаты, дневная и предоплаченная суммы, последняя корректировка и
связанный заказ на сегодня.

## Планировщик

- Генератор использует только зафиксированный `items` snapshot V2.
- Для старых строк без snapshot временно сохранён fallback на текущий каталог.
- Сумма snapshot обязана совпадать с `daily_total`; нарушение считается
  повреждением данных и обрабатывается fail-closed.
- Идемпотентность ежедневной генерации по-прежнему гарантирует уникальность
  `(company_id, recurring_order_id, service_date)`.
- При переходе на несколько backend workers планировщик нужно вынести в
  отдельный worker/beat. Уникальный индекс останется последней защитой.

## Миграция и приёмка

- Alembic revision: `9d3f1c7a2b60`.
- Перед production: backup, build backend/admin, `alembic upgrade head`,
  smoke новых API и проверка ролей.
- На Android: создать два разных постоянных заказа; изменить только второй;
  добавить/убрать товар; сменить время и филиал; проверить пересчёт; обновить
  приложение после сна; отменить с подтверждением; сверить дашборд и заказ на
  сегодня.
