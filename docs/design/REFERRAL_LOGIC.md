# Реферальная система SweetTime: личный QR и защита от накрутки

Дата: 2026-07-09. Обновлено: 2026-07-22. Статус: Flutter и серверная бизнес-логика реализованы;
публичная invite-страница/App Links ждут отдельного production rollout.

## Личный QR пользователя

У каждого пользователя есть постоянный буквенно-цифровой код (например,
`SWEETT-AB12CD`). После внедрения invite-links QR разделены по назначению:

1. **Карта лояльности** — payload `SWEETTIME:LOYALTY:<code>`, бариста сканирует
   на кассе для начисления/списания баллов.
2. **Приглашение друга** — HTTPS App Link
   `https://lnp-corporation.duckdns.org/invite/sweettime/<code>`. Если приложение
   установлено, ссылка сразу открывает экран приглашения; иначе открывается
   посадочная страница установки. Код сохраняется до завершения регистрации.

UI: центральная вкладка «QR» → три вкладки: «Мой QR» (лояльность),
«Пригласить» (HTTPS QR, системный share, копирование ссылки) и «Сканировать»
(камера + ручной ввод кода).

## Сравнение подходов к рефералке

| | A. Одноразовая привязка «один родитель» (дерево) | B. Взаимные сканирования с кулдауном | C. Многоуровневая (% с уровней, MLM) |
|---|---|---|---|
| Суть | У пользователя ровно один «пригласивший», привязка задаётся один раз при регистрации | Любые два юзера могут сканировать друг друга, лимит по времени | Бонусы с заказов приглашённых 2–3 уровней вглубь |
| Накрутка | ❌ невозможна взаимная: приглашённым может стать только новый аккаунт | ⚠️ фермится парами аккаунтов, нужны сложные эвристики | ⚠️ стимулирует создание фейковых веток |
| Сложность | Низкая: одно nullable-поле + 2 события | Средняя: журнал сканирований, кулдауны, пары | Высокая: обход дерева, начисления процентов |
| Понятность клиенту | «Приведи друга — получи 100» | Непрозрачно | Сложно объяснить, репутационные риски |
| Соответствие MVP-дефолтам (50/100) | ✅ точно | частично | нет |

**Выбор: подход A** — каждый пользователь может быть приглашён ровно один раз, только пока он
«новый». Получается лес деревьев (у узла один родитель), циклы невозможны по построению.

## Правила (зашиты в UX и backend)

1. **Один пригласивший навсегда.** Поле `invited_by` записывается один раз и не меняется.
   Повторное сканирование любого кода → «Вы уже были приглашены».
2. **Приглашённым может стать только новый клиент**: аккаунт без единого выполненного заказа
   (и, на backend, моложе 7 дней). Это убивает взаимную накрутку: если A пригласил B, то B не
   может «пригласить» A — A уже не новый.
3. **Нельзя пригласить себя** (код совпадает со своим).
4. **Деньги двигаются только после реального заказа**: приглашённому начисляется настроенный
   `invitedBonus` сразу при привязке (MVP-дефолт +50), пригласившему `inviterBonus`
   (MVP-дефолт +100) — **только после первого выполненного заказа** приглашённого. Ферма
   аккаунтов без реальных покупок не приносит пригласившему ничего.
5. **Один номер телефона = один аккаунт** (OTP-регистрация — естественный дедуп на backend).
6. **Лимиты пригласившего** (backend): максимум 20 начисленных приглашений в месяц; при
   превышении — привязка работает, бонус в очередь на ручную проверку.
7. Реферальные баллы живут по общим правилам (сгорают через 12 месяцев).

Дерево пользователей (`invited_by` как parent) остаётся в данных — пригодится для аналитики
«кто привёл сколько клиентов» в админке, без многоуровневых выплат.

## Поток

```
Друг (новый клиент)                      Я (пригласивший)
        |                                        |
        |  открывает ссылку / сканирует invite QR| вкладка QR → «Пригласить»
        |────────────────────────────────────────▶|
        |  проверки: не сам себя, не приглашён,  |
        |  нет выполненных заказов               |
        |  ✅ привязка invited_by + друг +50     |
        |                                        |
        |──── первый выполненный заказ ────────▶ | +100 баллов
```

## Backend (этап 2)

- `users.invited_by_user_id` — nullable FK, записывается один раз (constraint на UPDATE).
- `referral_events(id, inviter_id, invited_id, status: bound|rewarded|rejected, created_at)`.
- Начисление +100 — по событию первого заказа со статусом `completed` (идемпотентно).
- Код пользователя — короткий уникальный ID (6 цифр), генерируется при регистрации.

## Демо-реализация во Flutter (сделано)

- `applyReferral(code)` в `lib/shared/app_state.dart` отправляет код на backend; правила, начисления и
  защита от повторов остаются server-owned. Клиент дополнительно объединяет конкурентные вызовы в
  один запрос, чтобы восстановление сессии и auth-навигация не отправляли один код дважды.
- Вкладка QR: `lib/features/qr/qr_page.dart` (qr_flutter + mobile_scanner, ручной ввод кода
  как fallback без камеры).
- QR, экран баллов, результат активации и диалог первого заказа показывают актуальные
  `invitedBonus`/`inviterBonus` из company config.
