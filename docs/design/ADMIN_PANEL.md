# SweetTime Admin — единая мультитенантная админ-панель (white-label SaaS)

Дата: 2026-07-09. Статус: утверждённая концепция, MVP в разработке (папка `admin/`).

## Концепция

**Одна админка на всех бизнес-клиентов.** Не десятки отдельных панелей, а один продукт и один
деплой: каждая компания (кофейня/сеть) заходит под своей учётной записью и видит только свои
данные — меню, заказы, филиалы, сотрудников, настройки приложения. Компании не знают и не
могут узнать друг о друге. Это стандартная модель SaaS (Shopify, Poster, iiko).

Почему это правильно (оценка оркестратора):
- **Дешевле развивать**: одна кодовая база, фича сразу у всех клиентов, один pipeline деплоя.
- **Уже заложено в проект**: CLAUDE.md требует `company_id` в моделях для white-label; «full
  SaaS tenant management» стоит в Future.
- **Продаётся**: «свой брендированный апп + готовая админка» — сильное коммерческое предложение.

Главный риск — **изоляция данных**. Правило: ни один экран и ни один запрос не обращается к
данным без фильтра по `companyId` текущей сессии. В админке это тенант-скоупнутый data-слой,
на backend — фильтрация в зависимостях/репозиториях (не в хендлерах).

## Модель тенантов и ролей

- `Company` — тенант: id, название, брендинг (название приложения, акцентный цвет, логотип),
  валюта, настройки лояльности (%, лимит списания, срок сгорания), фичи-флаги (QR-заказ,
  постоянный заказ и т.п.).
- `AdminUser` — сотрудник компании: email, роль, companyId. Роли:
  - **owner** — всё, включая настройки приложения, тарифы, сотрудников;
  - **manager** — операционка: меню, заказы, филиалы, промо, аналитика;
  - **barista** — только очередь заказов своего филиала (простая, крупная).
- Все доменные сущности (продукты, заказы, филиалы, промо, клиенты) несут `companyId`.

## Стек

Next.js + TypeScript + Tailwind (кастомная, НЕ React Admin): нужен свой дизайн под токены
SweetTime и нестандартные экраны (брендинг-редактор, очередь заказов). Дизайн-токены — из
`DESIGN_SYSTEM.md` (candy/mint/coffee/cream, Inter), но стиль **операционный**: плотные
таблицы, быстрые действия, минимум декора. MVP работает на мок-данных (слой `admin/lib/`,
две демо-компании), подключение к FastAPI — на этапе Backend. Черновик React Admin от Codex
перенесён в `admin-legacy/`.

## Экраны MVP

| Экран | Роли | Содержимое |
|---|---|---|
| Вход | все | email+пароль (демо-аккаунты двух компаний), выбор роли демо |
| Dashboard | owner, manager | счётчики дня: заказы, выручка, средний чек, активные «постоянные заказы» |
| Заказы (очередь) | все | статусы Новый→Готовится→Готов→Выдан/Отменён, крупные кнопки смены статуса, фильтр по филиалу |
| Меню | owner, manager | товары: название, категория, цена (сом), модификаторы (размер/топпинги), доступность по филиалам, вкл/выкл |
| Филиалы | owner, manager | адрес, часы, телефон, доступность товаров |
| Сотрудники | owner | список, роль, филиал |
| Настройки приложения | owner | брендинг: имя приложения, акцентный цвет, логотип + живое превью телефона; правила лояльности и рефералки |

Демо-компании мок-слоя: **SweetTime** (данные из приложения: 8 напитков, 3 филиала Бишкека) и
**CoffeeGo** (контрастный набор: другой цвет бренда, другое меню) — чтобы на демо показать
изоляцию: перелогин → совсем другие данные и брендинг.

## Критерии приёмки MVP

1. Вход под SweetTime и под CoffeeGo показывает разные данные, брендинг и название — нигде не
   «просачиваются» данные чужой компании.
2. Роль barista видит только очередь заказов; owner видит всё.
3. Статус заказа меняется в 1 клик, очередь обновляется.
4. Настройки брендинга меняют превью приложения на лету.
5. Русский язык, суммы в сомах, дизайн-токены SweetTime.
6. `pnpm typecheck` и `pnpm build` проходят; страницы отвечают 200.
