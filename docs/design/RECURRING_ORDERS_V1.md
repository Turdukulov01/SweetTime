# Постоянные заказы v1 — спецификация (с push-уведомлениями)

Статус: черновик на утверждение. Автор: Claude. Дата: 2026-07-24.
Цель: превратить сохранённую предоплаченную подписку в реально работающий поток —
заказ создаётся к назначенному времени, виден клиенту в истории и заранее виден
персоналу в админке (без «внезапных» заказов в час-пик), с push за N минут.

## Что уже есть (не трогаем ядро)
- Модель `RecurringOrder` (одна на клиента): `product_ids`, `time` "HH:MM" (локальное
  время кофейни), `branch_id`, `plan` (single|week|month), `paid_until` (UTC, серверный), `active`.
- CRUD `/customer/me/recurring` (GET/PUT/DELETE) + экран подписки в приложении.
- **Нет** генерации заказов, планировщика, видимости в админке, метки в истории, пушей.

## Ключевые решения
1. **Таймзона кофейни: Asia/Bishkek (UTC+6)**, по умолчанию для всех. Позже — поле у компании.
   Планировщик переводит `time` "HH:MM" локального дня → момент UTC.
2. **Генерируем ЗАРАНЕЕ, готовим СВЕЖИМ.** Заказ на сегодня создаётся утром в статусе
   `scheduled` (виден в расписании, но не в активной очереди). За `prep_lead` минут до времени
   (по умолчанию 10) он «активируется»: `scheduled → new`, попадает в рабочую очередь, и уходит
   push. Так персонал видит план весь день, но делает свежим к времени.
3. **Идемпотентность в БД, а не в планировщике.** Уникальный ключ
   `(company_id, recurring_order_id, service_date)` — повтор тика/рестарт не создаёт дубль.
4. **Планировщик v1 — в процессе backend** (asyncio-таск в lifespan, тик раз в 60с). Backend
   запущен одним uvicorn-воркером, поэтому дублей нет; безопасность гарантируется ключом из п.3.
   celery/redis оставляем на будущее (масштабирование/несколько воркеров).

## Изменения данных (миграция)
Новые поля у `orders`:
- `recurring_order_id: str | null` (FK → recurring_orders.id, SET NULL) — источник = постоянный заказ.
- `scheduled_for: datetime(tz) | null` — целевой момент выдачи (UTC).
- `service_date: str | null` — локальная дата обслуживания "YYYY-MM-DD" (для идемпотентности).
- Новый уникальный индекс `uq_order_recurring_service_date (company_id, recurring_order_id, service_date)`
  (partial: только где `recurring_order_id` не null).
- Новое значение `status`: **`scheduled`** (запланирован, ещё не в активной очереди). Существующие
  `new|preparing|ready|done|cancelled` — без изменений.

Опционально у `companies` (или конфиг компании): `timezone` (default `Asia/Bishkek`),
`recurring_prep_lead_minutes` (default 10). Для v1 можно захардкодить дефолты в конфиге.

## Логика планировщика (тик раз в 60с)
1. **generate_due(today_local)**: для каждой активной подписки, где `paid_until >= now` и сегодня —
   день плана, если нет заказа с этим `(recurring_order_id, service_date)` → создать `Order`:
   `status=scheduled`, `type=scheduled`, `ready_time=time`, `scheduled_for=<UTC времени>`,
   `service_date=<локальная дата>`, товары/цены — серверный snapshot (как обычный заказ),
   `customer_id`, `branch_*`, `number` — как у обычных (свой префикс/счётчик).
   - «День плана»: single = только на дату оформления; week = каждый день 7 дней от оформления;
     month = каждый день до `paid_until`. (Точную семантику дней подтвердить — см. вопросы.)
2. **activate_ready(now)**: заказы `scheduled`, у которых `scheduled_for - now <= prep_lead` →
   `status=new` + push клиенту «Готовим ваш постоянный заказ к HH:MM» и (позже) сигнал в админку.
3. Всё в UTC; сравнение с локальным днём — через таймзону кофейни.

## Админка — «Расписание постоянных»
- Отдельная панель/страница: заказы на сегодня из постоянных, отсортированы по времени, видны
  ВЕСЬ ДЕНЬ заранее: «18:36 — Нурдан — Клубничный моти-кап + Матча · [запланирован|готовим]».
- Ближе к времени (активированные) подсвечиваются «пора готовить, к 18:36, свежий».
- Обычная очередь заказов показывает активированные постоянные заказы с меткой «постоянный, к HH:MM».
- Решает час-пик: никаких внезапных заказов — план виден заранее.

## Редактирование подписки (решение владельца 2026-07-24)

Время НЕ статично — клиент сам выбирает "HH:MM" (18:36 в примерах — иллюстрация).
После создания подписку можно править: состав, время, филиал, пожелания (comment).

- **PUT** (существующий) = покупка/продление: выбирает тариф, сервер пересчитывает
  `paid_until`. Принимает опц. `comment`.
- **PATCH** (новый) = редактирование активной подписки БЕЗ смены тарифа и срока:
  `{productIds?, time?, branchId?, comment?}`. `paid_until`/`plan` не трогаются —
  иначе каждая правка бесплатно продлевала бы подписку. 404 без активной подписки.
- **Цена всегда серверная**: ответ подписки несёт `dailyTotal` (сумма по текущему
  каталогу — честная цифра после правок и смены цен), а каждый сгенерированный заказ
  снапшотит актуальные цены как обычный заказ. При реальных платежах доплата за
  расширение состава станет отдельным флоу (v1 — demo-оплата).
- `comment` подписки копируется в каждый сгенерированный заказ (пожелания клиента
  видит бариста).

Статус: реализовано в backend (commit 931d983, тесты 100/100).

## Приложение (Flutter)
- Сгенерированный заказ уже попадает в историю (это реальный `Order` с `customer_id`). Добавляем в
  выдачу заказа флаг `isRecurring` (из `recurring_order_id != null`) → в истории метка
  «Постоянный заказ», остальная информация как обычно.

## Push-уведомления (FCM) — ВНЕШНЯЯ ЗАВИСИМОСТЬ
Требуется настройка Firebase (делает владелец, см. отдельные шаги):
- Проект Firebase + Android-приложение `kg.sweettime.app` → `google-services.json` в `android/app/`.
- Сервисный аккаунт (Admin SDK JSON) на backend для отправки (env-секрет, не в git).
- Flutter: `firebase_core` + `firebase_messaging`, регистрация device-token → новый эндпоинт
  `POST /customer/me/push-tokens`. Backend хранит токены и шлёт при активации заказа.
- Разрешение на уведомления (Android 13+ POST_NOTIFICATIONS) спрашиваем у пользователя.
Push — **этап 2**; ядро (генерация + расписание + метка) работает и без него.

## План по этапам
- **Э1 (backend, без внешних деп):** миграция + поля Order + функции generate/activate + тесты.
- **Э2 (backend):** планировщик в lifespan + серверная выдача `isRecurring` + расписание-эндпоинт для админки.
- **Э3 (admin):** страница «Расписание постоянных» + метка в очереди.
- **Э4 (Flutter):** метка «Постоянный заказ» в истории.
- **Э5 (push, после Firebase):** токены, отправка при активации, разрешения.

## Открытые вопросы к владельцу
1. Таймзона Asia/Bishkek — ок? `prep_lead` = 10 минут — ок?
2. Семантика дней недели/месяца: «каждый день» до конца оплаченного периода — так? Или выбранные
   дни недели? (v1 предлагаю «каждый день», как сейчас в подписке.)
3. Оплата: сейчас `paid_until` считается от оформления; генерация заказов трактует их как уже
   оплаченные (деньги — не черновик). Подтвердить, что списаний за каждый день нет (подписка).
