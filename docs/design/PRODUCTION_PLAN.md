# SweetTime — план боевого запуска (Phase 2 Backend + деплой)

Дата: 2026-07-13. Решение пользователя: боевой запуск (правильно), хостинг — **свой физический
сервер** (защищён, уже крутит 1 проект), выкладываем **API + админку**.

## 0. Честный статус (почему нельзя просто «залить»)

Два backend в репозитории, ни один не готов «как есть»:

| | `backend/app_demo` (демо-мост) | `backend/app` (черновик Codex под Postgres) |
|---|---|---|
| БД | SQLite | типизированный SQLAlchemy 2, но create_all, **без Alembic** |
| Авторизация | ❌ нет | ✅ JWT (register/login/refresh/OTP/me/delete), хэш паролей |
| Мультитенантность | ✅ по `/api/companies/{cid}/...` (то, что уже используют оба клиента) | ⚠️ «одна компания по умолчанию» (`default_company`) — фактически single-tenant |
| Контракт админки | ✅ наша кастомная Next.js-админка | ⚠️ старый React-Admin (X-Total-Count) — не наша |
| Модели | products/branches/orders/news/promotions | богатые: users/roles/loyalty/referral/payments/promo/recurring |
| Цены | ⚠️ приходят с клиента | частично серверные (services.py) |

**Канонический выбор (Task 5): эволюционируем контракт `app_demo`** (`/api/companies/{cid}/...`,
camelCase) — его уже понимают и приложение, и админка — и **вносим в него боевые механизмы из
`backend/app`**: JWT/хэш паролей (`security.py`), модели пользователей/лояльности/рефералки,
серверный расчёт цен. Так клиенты почти не переписываются, а безопасность становится боевой.

## 1. Что закрыть до выката (безопасность — обязательна)

1. **PostgreSQL + Alembic** — реальная БД, миграции с нуля, идемпотентный сид, раздельные
   demo/боевой датасеты.
2. **Авторизация (JWT)**: клиенты (OTP-вход по телефону) и сотрудники админки (email+пароль),
   access/refresh, logout/revocation, срок жизни. Пароли/секреты никогда не в ответах.
3. **Мультитенантность на сервере**: `company_id` берётся из токена, а не из URL/клиента; каждый
   запрос жёстко скоуплен. Утечка между компаниями = блокер.
4. **RBAC**: owner/manager/barista/customer — права на ресурс и действие; бариста не трогает
   настройки; клиент не двигает статусы.
5. **Серверные цены/итоги**: сервер пересчитывает сумму, модификаторы, лимит списания баллов
   (30%), начисление (5%), сгорание (12 мес) — не доверять клиенту.
6. **Правила заказа**: разрешённые переходы статусов, идемпотентное завершение/возврат.
7. **Рефералка**: `invited_by` один раз, +100 идемпотентно после первого выполненного заказа,
   анти-фрод лимиты.
8. **Провайдеры-заглушки** (OTP/оплата/чек) за интерфейсом — реальные только после договорённостей.
9. **Тесты** бизнес-правил и изоляции на Postgres.

## 2. Клиенты (после боевого API)

- **Flutter**: `API_BASE` → боевой URL (напр. `https://api.<домен>`); добавить хранение токена
  (`flutter_secure_storage`), реальный OTP-flow вместо демо-кода, обработку 401/refresh.
- **Админка**: `NEXT_PUBLIC_API_URL` → боевой URL; заменить localStorage-сессию на JWT-логин.

## 3. Деплой на физический сервер (коэкзистенция с существующим проектом)

Архитектура (Docker Compose, отдельный стек, чтобы НЕ трогать текущий проект сервера):
- контейнеры: `api` (FastAPI/uvicorn+gunicorn), `db` (Postgres + volume), `admin` (Next.js
  standalone), опц. `redis`;
- **reverse-proxy** (nginx/Caddy/Traefik — тот, что уже на сервере) на поддомены:
  `api.<домен>` → api, `admin.<домен>` → admin; **TLS** (Let's Encrypt);
- НЕ занимать порты существующего проекта; свои внутренние порты + проксирование по домену;
- бэкапы БД (pg_dump по cron), переменные окружения/секреты в `.env` на сервере (не в git),
  логи, автоперезапуск (restart: unless-stopped).

### Что нужно от тебя для этого этапа (соберём к деплою)
- ОС сервера (Linux-дистрибутив?), есть ли Docker/Compose;
- как выложен текущий проект (Docker? nginx/Caddy/Traefik? какие порты/домены заняты);
- домен/поддомен для SweetTime (или деплоим на IP:порт временно);
- как я получу доступ: ты выполняешь мои команды по шагам / даёшь ограниченный SSH;
- есть ли уже Postgres на сервере или поднимаем свой контейнер.

## 4. Порядок работ (staged, каждый шаг — коммит, откат через git)

- **S1. Каноническая основа**: выбрать/собрать боевой пакет; Postgres-конфиг; Alembic init +
  первая миграция; модели (company/user/role + каталог/заказы/контент); сид demo+боевой.
- **S2. Авторизация и RBAC**: JWT клиент/сотрудник, refresh/logout, скоуп по company_id из токена,
  роли. Тесты изоляции.
- **S3. Боевые правила**: серверные цены/лояльность/рефералка/статусы + тесты.
- **S4. Контент и админ-CRUD** под нашу Next.js-админку (news/promotions/products-флаги + защита).
- **S5. Клиенты на боевой API**: Flutter (токены/OTP), админка (JWT-логин).
- **S6. Деплой-артефакты**: Dockerfile(api/admin), docker-compose.prod, nginx/TLS, .env-шаблоны,
  бэкапы, healthcheck.
- **S7. Выкат на сервер** рядом с существующим проектом, smoke-тесты, приёмка.

## Примечание
Demo-мост `backend/app_demo` остаётся для локальной разработки/скриншотов, боевой пакет — отдельно
и явно. Реальные оплаты/SMS — только после провайдеров и договорённостей (CLAUDE.md).
